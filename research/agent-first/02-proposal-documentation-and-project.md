## 1. Зачем нужен этот документ

Владелец попросил начать следующий этап с решений, которые задают направление
структуре проекта, но не требуют немедленной перестройки всех репозиториев.
Предлагается сначала согласовать компактную модель, затем опробовать ее на
самой `mother` и на одном-двух пилотах.

Документ отвечает на четыре вопроса:

1. где хранить решения, функции, исследования, первичные материалы, фикстуры,
   блокеры, обратную связь агента, визуализации и константы;
2. как разделить brief, proposal, research, architecture, plan и evidence;
3. как сделать Issue подходящей для feature, bug, UI-задачи и документации;
4. какие поля, статусы и views нужны для текущего Project.

Все формулировки ниже являются предложениями, если в разделе 8 не указано,
что направление уже подтверждено владельцем. Пилотные изменения Project,
которые явно согласованы в review, можно применять к этому Project. Массовую
миграцию других репозиториев начинать не следует.

## 2. Что проверено фактически

### 2.1. Репозиторий

- До подготовки этого proposal рабочее дерево было чистым, а ветка `main` была
  синхронизирована с `origin/main`.
- Репозиторий содержит документацию и исследовательские материалы. Приложение,
  package manager, тестовый набор и CI для исходного кода отсутствуют.
- Текущий handoff указывает на проверку Project, подготовку proposal и
  последующее согласование.

### 2.2. Organization Project

Проверен приватный organization-level Project [Project methodology
matrix](https://github.com/orgs/vernikr/projects/1):

| Наблюдение | Текущее значение |
|---|---|
| Владелец | organization `vernikr` |
| Items | 1 |
| Item | Issue #1 из `vernikr/mother` |
| Status Issue #1 | `In Progress` |
| Views | `All work` (table), `Queue` (board), `Blocked` (table) |
| Статусы | `Inbox`, `Ready`, `In Progress`, `Blocked`, `Done` |
| Пользовательские поля | organization-level `Business Value`, number, шкала `0–5` |
| Системные поля | Title, Assignees, Status, Labels, Linked pull requests, Milestone, Repository, Reviewers, Parent issue, Sub-issues progress, Created, Updated, Closed |
| Включенные workflows | auto-add sub-issues, auto-close issue, item added, item closed, pull request linked, pull request merged |

Project уже organization-level, поэтому его техническая модель допускает items
из нескольких репозиториев. Поле `Repository` является системным и не требует
дублирования в отдельном пользовательском поле.

### 2.3. Проверенные ограничения GitHub

Официальная документация подтверждает несколько важных для proposal свойств:

- Project может использовать несколько views и пользовательские поля разных
  типов: number, single-select, text, date и iteration.
- Issue fields задаются на уровне организации и остаются одинаковыми во всех
  Projects, куда входит Issue. Project fields принадлежат одному Project.
- GitHub рекомендует выбирать один источник истины и автоматически отражает в
  Project такие данные Issue, как labels, assignees и milestones.
- Встроенные workflows можно дополнять Actions и GraphQL API, но их нужно
  проверять по фактическому состоянию перед тем, как считать lifecycle
  полностью автоматическим.

Источники: [Best practices for
Projects](https://docs.github.com/en/issues/planning-and-tracking-with-projects/learning-about-projects/best-practices-for-projects),
[Managing issue fields in your
organization](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/managing-issue-fields-in-your-organization),
[Using the API to manage

## 3. Предлагаемая иерархия материалов

Предлагается использовать небольшой baseline и добавлять каталоги только при
первой реальной потребности. Для `mother` это пока схема проектирования, а не
команда создать весь набор каталогов сразу.

```text
project/
├── AGENTS.md
├── README.md
├── FEATURES.md
├── ALGORITHMS.md                  # optional; one compact overview by default
├── FOLLOW-UPS.md                  # optional ideas, not the task backlog
├── docs/
│   ├── index.md
│   ├── architecture.md или architecture/
│   ├── research/
│   │   ├── index.md
│   │   └── <research-id>-short-slug/
│   │       ├── brief.md
│   │       ├── report.md
│   │       └── materials/
│   ├── proposals/
│   ├── plans/
│   │   ├── active/
│   │   └── completed/
│   └── constants.md
├── decisions/
│   ├── index.md
│   └── 0001-short-slug.md
├── tests/
│   └── fixtures/                  # default location for test-only fixtures
└── feedback/
    ├── inbox/
    │   ├── inbox.md
    │   └── threads/
    ├── archive/
    └── outbox.md
```

### 3.1. Decisions

Предлагается принять каталог `decisions/` как долговечный журнал решений:

- `decisions/index.md` содержит кликабельное оглавление, если список решений
  стал достаточно большим, и короткие тематические разделы с подразделами;
- в таблице index вместо отвлеченного названия выводится само решение — или
  вопрос, если решение еще не принято. Формулировка должна быть очень краткой,
  по возможности на языке бизнеса, с минимумом ссылок на кодовые артефакты;
- рекомендуемые колонки: ID, решение или вопрос, состояние, связанные Issue и
  ссылка на подробную запись;
- подробная запись имеет имя `0001-short-slug.md`;
- запись включает исходный вопрос, варианты с плюсами и минусами, выбранный
  вариант, обоснование, последствия, доказательства и связанные Issue;
- в index достаточно различать `open` и `closed`: `open` означает, что вопрос
  еще требует решения владельца, а `closed` — что оперативного выбора больше
  не требуется; принято ли решение, отклонено или заменено новым, указывается
  в тексте самой записи;
- новая запись появляется после согласования решения, а proposal остается
  исследовательским материалом, если он больше не нужен для работы.

Дата не является обязательной колонкой: этот проект описывает развивающуюся
систему, а не хронологический журнал. Если для конкретного решения понадобится
различать принятое решение и замененное новым, это можно указать в тексте
записи и ссылкой на заменяющую запись, не расширяя базовый index.

Нумерация дает стабильные ссылки и не требует поддерживать большую
тематическую таксономию. Группировку лучше делать через index и ссылки, а не
через вложенные каталоги.

Пример строки index:

```markdown
| ID | Решение или вопрос | Состояние | Issue |
|---|---|---|---|
| [0001](0001-bv-field.md) | Оценивать ценность работы по шкале 0–5 | closed | #1 |
| [0002](0002-project-statuses.md) | Какие статусы нужны для очереди агента? | open | #1 |
```

Секция решений может быть организована, например, по темам `Документация`,
`Управление работой`, `Проверка` и `Профили проектов`. Это группировка для
навигации, а не новая таксономия, которую нужно поддерживать любой ценой.

### 3.2. Feature tree

После чтения приложенной переписки стало ясно, что здесь нужен не обычный
реестр функций и не формальная декомпозиция с обязательными типами узлов.
Нужен отдельный, постоянно просматриваемый документ с компактным деревом
конечного функционального охвата. Дерево должно отражать структуру мысли,
допускать смешанные смысловые категории, свободную глубину и итеративную
глобальную редактуру.

Предлагается вынести его в корень как `FEATURES.md`:

```text
- Основная возможность
  - Подвозможность
    - Вариант или ограничение
```

`FEATURES.md` не должен содержать текущие статусы задач, планы или подробную
архитектуру. Его задача — дать владельцу возможность одним взглядом проверить,
не уплыл ли функциональный охват продукта. Он также должен быть достаточно
самодостаточным, чтобы другой агент мог восстановить требуемую функциональность
без копирования конкретной реализации.

FR-ID не предлагается делать обязательным элементом дерева. Идентификаторы
можно добавить позже для отдельных ветвей, если появится практическая польза
для связки с Issue, тестами или несколькими репозиториями. Это отдельный
вопрос, который не следует решать до появления собственного концепта дерева.

Для построения и редактирования дерева предлагается использовать пять
проходов: полнота, структура, сжатие, проверка полноты и читаемости, повторная
редактура. В финальном файле сохраняется только дерево без истории проходов и
пояснительных абзацев.

### 3.3. Research и первичные материалы

Предлагается хранить новые исследования в `docs/research/`. Это делает их
частью долговечной документации и позволяет находить их через единый индекс
документов. Существующий `research/agent-first/` остается историческим
расположением текущего исследования; его возможная миграция обсуждается
отдельно и не входит в этот proposal.

Для одного исследования:

- `brief.md` фиксирует вопрос, scope, критерии достаточности и ограничения;
- `report.md` содержит выводы и сам список использованных источников;
- `materials/` содержит первичные документы или их локальные копии, когда это
  разрешено и действительно нужно для воспроизводимости;
- крупные или чувствительные материалы не включаются автоматически в Git.

Индекс `docs/research/index.md` нужен, когда исследований стало больше одного
или их нужно находить из нового контекста. Для одного короткого исследования
он может быть отложен.

### 3.4. Fixtures

Предлагается использовать `tests/fixtures/` по умолчанию, если фикстуры нужны
только тестам. Это держит тестовые материалы рядом с проверяемым поведением и
не раздувает корень проекта.

Верхнеуровневый `fixtures/` нужен только тогда, когда один и тот же материал
используют тесты, демо, e2e, eval или несколько независимых инструментов.
Фикстуры не должны быть скрытым архивом первичных материалов:

- исследовательский оригинал остается в `docs/research/.../materials/`;
- тестовый образец остается в `tests/fixtures/` или в общем `fixtures/` по
  описанному выше правилу;
- каждый нетривиальный fixture получает короткое описание происхождения и
  ожидаемого использования.

### 3.5. Blockers

Предлагается не создавать `docs/blockers/` в базовой структуре. Каноническая
запись блокера остается в самом Issue: причина, затронутая работа, ожидаемое
внешнее действие, способ повторной проверки и ссылка на зависимость. Project
показывает такие Issue через отдельный статус `Blocked` и отдельный view.

Отдельный документ понадобился бы только при доказанной проблеме: например,
если один внешний блокер одновременно удерживает несколько Issue и его нужно
описывать независимо от каждой из них. Это будет расширение после пилота, а не
обязательная папка. Такой подход уменьшает число мест, которые агент должен
синхронизировать.

### 3.6. Индекс документации

Предлагается переименовывать `docs/README.md` в `docs/index.md` только в
проектах, где каталог `docs/` стал самостоятельной картой знаний. В корневом
`README.md` остается краткий вход: назначение, quickstart и ссылки на главные
разделы. `docs/index.md` отвечает на вопрос «какой документ читать для какой
задачи» и не повторяет описание продукта.

Практическое правило: создавать `docs/index.md`, когда в `docs/` появляется
несколько устойчивых разделов, несколько агентских маршрутов чтения или риск
потерять документ среди файлов. Пустой индекс ради симметрии не нужен.

Для отдельного документа, который длиннее двух-трех страниц, содержит несколько
разделов и предназначен для человеческого review, предлагается добавлять в
начало кликабельное Markdown-оглавление со ссылками на разделы и подразделы.
Детальная низкоуровневая документация, предназначенная главным образом для
агента и регулярно читаемая целиком, может обходиться без такого оглавления.

### 3.7. Feedback, reflection и follow-up inbox

Предлагается назвать общий каталог `feedback/`, потому что его задача шире
саморефлексии агента. Он остается условным профилем: маленький проект не
обязан собирать сырые threads или вести полный журнал общения.

| Каталог или файл | Назначение |
|---|---|
| `feedback/inbox/inbox.md` | Указатель на неразобранные сообщения, скриншоты и короткие заметки |
| `feedback/inbox/threads/` | Сохраненные человеком исходные threads и связанные материалы |
| `feedback/archive/` | Разобранные записи, которые больше не требуют оперативной работы |
| `feedback/outbox.md` | Выявленные принципы и системные улучшения, ожидающие интеграции |

`feedback/outbox.md` является временным рабочим списком. После интеграции
принцип переносится в канонический файл, например `AGENTS.md`, decision или
workflow, а запись убирается из outbox или помечается как обработанная.

Скриншот или thread сначала попадает в inbox с датой и контекстом, затем агент
либо удаляет шум, либо создает запись в archive, либо поднимает системное
изменение в Issue/decision. Обязательным этот workflow становится только для
проектов, которые реально используют такую обратную связь.

Неразобранные предложения и невыбранные follow-up prompts предлагается вынести
в корневой `FOLLOW-UPS.md`. Это ideas backlog с низкой обязательностью: наличие
идеи не означает, что она плохая, а отсутствие выбора не означает отказ.
Запись не попадает в GitHub Project до явного решения превратить ее в работу.

Сохранение исходного thread — операционная обязанность владельца или другого
инструмента, который может экспортировать текущий диалог. Агент может
обработать и записать thread, если его текст или файл передан в контекст, но не
может самовольно получить произвольный внешний чат или решить, какой экран
нужно сохранить. Поэтому `feedback/inbox/threads/` является входом для агента,
а не артефактом, который агент обязан создавать после каждой сессии.

### 3.8. Сложные алгоритмы

По умолчанию предлагается один файл `ALGORITHMS.md` в корне проекта. Он нужен
для быстрого обзора всей сложной логики и проверки того, что в ней нет
необъяснимых ветвлений. Отдельная папка `docs/algorithms/` появляется только
в большом проекте, когда один документ перестает оставаться обозримым.

Один документ или одна запись в нем содержит:

1. назначение и границы алгоритма;
2. входы, выходы и инварианты;
3. дерево условий или state machine в Mermaid либо другом переносимом формате;
4. таблицу ветвления с идентификаторами узлов;
5. примеры пограничных случаев;
6. команду генерации изображения, если картинка нужна для редкого
   человеческого просмотра.

Текстовая таблица и diagram source являются каноническими материалами.
Сгенерированная картинка считается производным артефактом и проверяется на
расхождение. Не следует вручную поддерживать картинку отдельно от описания.

### 3.9. Реестр констант

Для небольшого проекта предлагается один файл `docs/constants.md`. Каждая
строка реестра содержит:

| Поле | Смысл |
|---|---|
| ID или имя | Ссылка на константу в коде или конфигурации |
| Значение и единица | Число, строка, duration, размер и т. п. |
| Назначение и изменение | Что настраивает значение и что нужно проверить при его изменении |
| Обоснование и источник | Почему выбрано значение и откуда это известно; поле может быть пустым |

При росте числа записей файл можно разделить на `docs/constants/`, сохранив
`index.md` как навигацию. Агент сообщает о каждом новом значимом magic number
в completion report и либо добавляет его в registry, либо объясняет, почему
регистрация не нужна. Пустая ячейка в колонке «Обоснование и источник»
допустима: агент не должен придумывать обоснование только ради заполнения
таблицы.

## 4. Модель артефактов конкретной задачи

Предлагается разделить артефакты по сроку жизни и не создавать копии одного и
того же текста:

| Артефакт | Где живет | Когда нужен |
|---|---|---|
| Brief | Issue body или короткий `docs/proposals/`-вход | Всегда для крупной работы; для маленькой задачи достаточно Issue |
| Proposal | `docs/proposals/<issue>-short-slug.md` | Когда до реализации нужно сравнить варианты |
| Research | `docs/research/<id>-short-slug/` | Когда нужен внешний или внутренний сбор доказательств |
| Architecture | `docs/architecture.md` или `docs/architecture/` | Когда знание переживает одну задачу |
| Decision | `decisions/0001-short-slug.md` | После согласования важного выбора |
| Plan | `docs/plans/active/<issue>-short-slug.md` | Для multi-session, multi-repo или сложной проверки |
| Evidence | Реальные бизнес-показатели, замеры поведения, редкие screenshots и ссылки на результаты | Для подтверждения того, что изменилось для пользователя или владельца |

Issue остается источником смысла задачи: intent, scope, non-goals, acceptance
criteria и требуемое evidence. Документ не должен заново копировать эти поля.
Он может содержать ссылку на Issue и детали, которые слишком объемны или
долговечны для ее body. Успешный CI/CD считается базовым условием и не обязан
становиться отдельным бизнес-evidence. Скриншоты добавляются только когда они
действительно помогают проверить результат, потому что они увеличивают
контекст и стоимость чтения.

После принятия proposal его существенное решение переносится в numbered
decision. После завершения план переносится в `completed/` или остается с
явным статусом. Создание нового документа не создает новую Issue.

## 5. Адаптивный Issue template

Предлагается не делать одну форму с длинным набором полей. Лучше использовать
общий минимальный каркас и отдельные формы:

- `feature.yml` — пользовательская или агентская возможность;
- `bug.yml` — наблюдаемое неправильное поведение и воспроизведение;
- `ui.yml` — экран, визуальное поведение, accessibility и визуальное evidence;
- `documentation.yml` — изменение durable knowledge, структуры или процесса;
- `research.yml` — исследовательский вопрос, источники и критерии достаточности;
- `config.yml` — ссылки и предотвращение пустых Issue.

Обязательное ядро всех форм:

- intent или problem;
- affected repository и surface;
- scope и non-goals;
- acceptance criteria;
- required checks/evidence;
- dependencies и блокирующее решение владельца;
- ссылки на ветку `FEATURES.md`, proposal, research или decision, когда они
  существуют.

Различия между формами должны быть небольшими. Например, bug добавляет
steps-to-reproduce и expected/actual behavior, UI добавляет viewport и
визуальное доказательство, research добавляет search scope и stopping rule.
Так сохраняется единая модель работы без универсальной формы, перегруженной
неподходящими вопросами.

### 5.1. Что такое `.yml`

`.yml` — обычный текстовый YAML-файл, который GitHub использует как описание
полей формы. Это не исполняемый скрипт. Файл говорит GitHub, какие поля показать
при создании Issue и как собрать ответы в Markdown-тело Issue.

Минимальный пример `feature.yml`:

```yaml
name: Feature
description: Новая возможность продукта
title: "[Feature] "
body:
  - type: textarea
    id: intent
    attributes:
      label: Intent
      description: Какую возможность должен получить пользователь?
    validations:
      required: true
  - type: textarea
    id: acceptance
    attributes:
      label: Acceptance criteria
      description: Как проверить, что задача выполнена?
    validations:
      required: true
```

Варианты форм отличаются только дополнительными полями. В `bug.yml` это могут
быть `steps`, `expected` и `actual`; в `ui.yml` — `screen`, `viewport` и
`visual-evidence`; в `documentation.yml` — `source`, `audience` и `affected-docs`;
в `research.yml` — `question`, `scope`, `sources` и `stopping-rule`. Общие
поля можно повторять в каждом файле, если GitHub Issue Forms не предоставляет
подходящего механизма переиспользования. Их следует держать короткими и
одинаково называть, чтобы агенту не приходилось изучать несколько разных
терминологий.

Ниже приведены не готовые шаблоны для немедленного добавления, а небольшие
примеры формы каждой разновидности:

```yaml
# bug.yml
name: Bug
description: Неправильное или неожиданное поведение
body:
  - type: textarea
    id: steps
    attributes:
      label: Steps to reproduce
  - type: textarea
    id: expected
    attributes:
      label: Expected behavior
  - type: textarea
    id: actual
    attributes:
      label: Actual behavior
```

```yaml
# ui.yml
name: UI task
description: Изменение экрана или пользовательского взаимодействия
body:
  - type: input
    id: screen
    attributes:
      label: Screen or flow
  - type: input
    id: viewport
    attributes:
      label: Viewport or platform
  - type: textarea
    id: evidence
    attributes:
      label: Visual evidence
```

```yaml
# documentation.yml
name: Documentation
description: Изменение документации или процесса
body:
  - type: input
    id: source
    attributes:
      label: Source of truth
  - type: input
    id: audience
    attributes:
      label: Audience
  - type: textarea
    id: affected_docs
    attributes:
      label: Affected documents
```

```yaml
# research.yml
name: Research
description: Исследовательский вопрос
body:
  - type: textarea
    id: question
    attributes:
      label: Research question
  - type: textarea
    id: scope
    attributes:
      label: Scope and stopping rule
  - type: textarea
    id: sources
    attributes:
      label: Expected source types
```

После согласования формы можно дополнить общими `intent`, `scope`, `non-goals`,
`acceptance` и `evidence`. Наличие отдельного файла не означает отдельный
жизненный цикл: все формы создают обычные Issues и попадают в один Project.

## 6. Предлагаемая схема Project

### 6.1. Поля

Предлагается начать с минимального набора:

| Поле | Предложение | Обоснование |
|---|---|---|
| Status | Project field, расширить lifecycle | Нужен операционный путь от inbox до завершения и отдельное отображение блокеров |
| Business Value (BV) | Organization Issue field, number от 0 до 5 | Значение должно сохраняться между Projects и репозиториями |
| Type | Issue type или label | Тип уже относится к Issue и не должен дублироваться в Project |
| Repository | Встроенное поле | Уже поддерживает cross-repository Project |
| Priority | Пока не добавлять | Польза не доказана, а порядок волн можно задавать Issue и планом |
| Agent state | Пока не добавлять | Блокировку можно выразить отдельным статусом |
| Risk | Не добавлять | Владелец попросил убрать поле до появления ясной пользы |
| Iteration / Target date | Не добавлять | Календарное управление не входит в текущий operating model |
| Estimate / Effort | Не добавлять на пилоте | Сначала нужно проверить, будет ли это использоваться в views и отчетах |

### 6.2. Как трактовать BV

Предлагается использовать числовой `BV` с фиксированной шкалой:

| Значение | Рабочий смысл |
|---:|---|
| 0 | Нет подтвержденной ценности или исследование еще не прошло triage |
| 1 | Локальное удобство или небольшая экономия времени |
| 2 | Улучшение надежности, сопровождения или отдельного workflow |
| 3 | Пользовательская возможность для одного продукта |
| 4 | Существенная ценность для нескольких продуктов, репозиториев или workflow |
| 5 | Стратегическое основание, разблокирующее направление или значимая ценность для владельца |

Шкала является порядковой. Она не обещает математически точную ценность и не
должна автоматически превращаться в «ценность на строку кода».

Утилита `size-report` может поставлять evidence о приросте или изменении
кодовой базы. На первом этапе следует сохранять эти наблюдения отдельно и
смотреть на корреляцию `BV` с maintenance cost и code growth. Деление BV на
число строк создало бы ложную точность: большой feature может быть оправдан,
а маленькая правка может иметь высокий эффект.

### 6.3. Статусы и lifecycle

Предлагается заменить текущие три статуса на пять. Отдельный `Verify` не
нужен: агент выполняет тесты и другие проверки в рамках того же agent run, а
результат и реальные показатели фиксируются в Issue или completion report.

```text
Inbox → Ready → In progress → Done
                  └──────────→ Blocked
```

| Статус | Условие входа | Условие выхода |
|---|---|---|
| Inbox | Issue создана или получена из внешнего inbox | Intent, type, scope и BV прошли triage |
| Ready | Задача понятна и может быть взята | Агент начал работу или обнаружен blocker |
| In progress | Есть активный agent run или реализация | Реализация и проверки завершены, внешний blocker найден или работа остановлена |
| Blocked | Нужен владелец, внешний сервис или решение | Причина снята и задача возвращена в Ready/In progress |
| Done | Агент выполнил acceptance criteria и проверки, а evidence зафиксирован | Только reopen при новом факте |

Главная причина отдельного `Blocked` — не смешивать отсутствие работы с
ожиданием внешнего события. Свежий агент может быть привлечен для проверки
сложной или рискованной задачи, но это исключение, а не обязательный переход
жизненного цикла.

Текущие встроенные workflows `auto-close issue` и `pull request merged` нужно
проверить перед настройкой нового lifecycle: они не должны обходить требование
evidence перед `Done`. На этом этапе proposal намеренно не меняет их.

### 6.4. Views

Предлагается заменить безымянный `View 1` на небольшой набор:

1. `All work` — таблица без скрытого фильтра, источник полной видимости;
2. `Queue` — board по Status, только Inbox/Ready/In progress/Blocked;
3. `Blocked` — отдельный view только для заблокированных Issue с причиной,
   Repository, BV и ссылками на зависимость;
4. `By repository` — дополнительный view только для зонтичных Projects,
   охватывающих несколько репозиториев, например семейство Gemini.

Views являются проекциями. Они не создают дополнительные items и не становятся
отдельными списками задач.

## 7. Lifecycle Issue → agent run → evidence

Предлагается следующий минимальный протокол:

1. Агент создает или принимает Issue и проверяет, что аналогичного item нет.
2. Во время triage заполняет type, scope, acceptance criteria, BV и ссылки.
3. Issue переводится в `Ready` только после того, как следующий шаг понятен.
4. Перед изменением файлов агент перечитывает Issue и создает plan только при
   необходимости.
5. Во время работы агент сохраняет blockers и discoveries там, где они имеют
   долговечную ценность.
6. После реализации тот же агент выполняет тесты и другие обязательные
   проверки, прикладывает реальные бизнес-evidence и закрывает Issue, если
   acceptance criteria выполнены.
7. Свежий agent context или отдельный evaluator используется только для
   задач, где стоимость ошибки оправдывает дополнительный расход контекста.
8. После завершения Project и repository links перечитываются API-запросом.
9. Если проверка не пройдена, item остается в `In progress`; если причина
   внешняя, используется `Blocked`.

Этот протокол оставляет текущие Issue и Project источниками управления, а
репозиторий — источником durable knowledge и воспроизводимых процедур.

## 8. Что нужно согласовать до реализации

После review владельца зафиксированы следующие направления:

1. Использовать BV как числовое поле `0–5`.
2. Использовать organization-level Issue field для BV, чтобы значение было
   общим между Projects и репозиториями.
3. Не добавлять `Verify`; проверки выполняются тем же агентом в `In progress`.
4. Создать отдельный view `Blocked`.
5. Создать `By repository` только для зонтичных Projects.
6. Вынести дерево функциональности в корневой `FEATURES.md`, пока без
   обязательных FR-ID.
7. Хранить новые исследования в `docs/research/`, а источники записывать в
   самом report.
8. Использовать `feedback/inbox/inbox.md`, `feedback/inbox/threads/`,
   `feedback/archive/` и `feedback/outbox.md`.
9. Вынести идеи и невыбранные follow-ups в корневой `FOLLOW-UPS.md`.
10. Сохранять исходные threads силами владельца или инструмента экспорта;
    агент обрабатывает переданные ему файлы.

Остаются вопросы, которые лучше проверить на пилоте:

1. Нужно ли называть корневой файл дерева `FEATURES.md` или выбрать более
   точное имя вроде `FUNCTIONALITY.md`?
2. Достаточно ли `open` и `closed` для index решений, или нужно отдельно
   отличать принятое решение от решения, замененного новым?
3. Нужен ли `ALGORITHMS.md` в конкретном проекте, или достаточно добавлять его
   только после появления первой трудно обозримой логики?

До ответов владельца этот файл остается proposal. Следующий технический шаг
после согласования — применить только одобренные изменения к `mother`, затем
перечитать Project и проверить результат через API. Массовая миграция 37
репозиториев в этот этап не входит.

## 9. Новые профильные гайдлайны

Новые требования следует развивать как отдельные профили. Профиль применяется
только к проектам, где есть соответствующая потребность. Общий entry point для
такой работы — корневой [`MOTHER.md`](../../MOTHER.md).

### 9.1. Conformance entry point

`MOTHER.md` — короткая отправная инструкция для агента, которого попросили
привести другой проект в соответствие с mother. Она задает порядок чтения,
осмотр проекта перед изменениями, выбор применимых профилей, работу через
Issue, минимальность миграции, проверку и формат итогового отчета.

Детальная проработка и поддержание файла ведутся в [Issue #3](https://github.com/vernikr/mother/issues/3).

### 9.2. LLM и реестр промптов

Проекты, использующие LLM, должны получить отдельный профиль. Его центральный
артефакт — реестр промптов, где один Markdown-файл описывает один prompt.
Нужно отдельно определить единый формат подставляемых значений, metadata,
версий, вариантов для моделей, примеров и проверок. Детальная работа ведется
в [Issue #4](https://github.com/vernikr/mother/issues/4).

### 9.3. Fork divergence и Why this fork

Проекты-форки должны иметь корневой человекочитаемый реестр отличий от
оригинала. Он должен быть написан на языке бизнеса и служить источником для
раздела `Why this fork` в GitHub README. Наличие такого раздела в README —
требование для форков. Детальная работа ведется в [Issue #5](https://github.com/vernikr/mother/issues/5).

### 9.4. MCP, CLI skills и From GitHub

Проекты с MCP должны иметь соответствующие skills и описывать основные
операции через CLI, а не делать MCP единственным способом работы. Отдельно
нужно определить host-интеграцию для добавления MCP через UI вроде `From
GitHub`, включая роль Claude Code-файлов или других instruction/configuration
адаптеров. Детальная работа ведется в [Issue #6](https://github.com/vernikr/mother/issues/6).

### 9.5. Универсальное логирование

Для проектов, где логирование возможно и полезно, нужен общий функциональный
контракт, независимый от платформы. Минимальное уже зафиксированное требование:
каждая запись лога должна содержать исходного актора — `human`, `agent` или
`system`. В качестве исходных примеров нужно изучить `arena-bridge` и
`yt-summary`, учитывая, что их logging systems еще требуют доработки. Детальная
работа ведется в [Issue #7](https://github.com/vernikr/mother/issues/7).

### 9.6. Формат самих guidelines

Нужно отдельно решить, где должны жить reusable guidelines: в файлах
репозитория `mother`, в виде skills или в обоих форматах. Предварительная
рабочая гипотеза:

- репозиторный документ является каноническим источником требований,
  терминологии, примеров и acceptance criteria;
- skill является on-demand процедурой: он подсказывает агенту, как применить
  guideline, провести проверку или выполнить миграцию;
- skill не дублирует подробный документ, а ссылается на него и добавляет
  исполнимый workflow;
- простой guideline может быть только документом, а guideline с повторяемой
  процедурой может иметь пару «документ + skill».

Это пока гипотеза. Ее нужно проверить на нескольких профилях и на реальном
повторном использовании. Отдельная проработка ведется в [Issue #8](https://github.com/vernikr/mother/issues/8).

### 9.7. Общие требования к UI/UX

Нужен отдельный универсальный документ с функциональными требованиями к UI/UX,
который применим и к GUI, и к TUI. Базовая часть должна описывать общие
принципы взаимодействия, обратную связь, состояния, ошибки, навигацию,
доступность и проверяемость. GUI- и TUI-специфичные различия должны быть
отдельными расширениями, а не двумя противоречащими стандартами.

Формат и место такого документа пока не утверждены. Проработка ведется в
[Issue #9](https://github.com/vernikr/mother/issues/9).

### 9.8. Единый стек и версии инструментов

Нужно постепенно сократить зоопарк фреймворков, runtime, пакетных менеджеров и
их версий. Это не означает один стек для всех проектов. Нужна матрица
поддерживаемых вариантов по профилям с явными версиями, сроком поддержки,
исключениями и процедурой миграции. Первые наработки владельца должны стать
входными материалами для отдельного исследования в [Issue #10](https://github.com/vernikr/mother/issues/10).

### 9.9. Отслеживание соответствия проектов

Для каждого из 37 проектов нужно будет видеть не только наличие общей задачи,
но и прогресс по отдельным измерениям: документация, Project, стек,
функциональные модули и применимые профильные guidelines. Один проект может
иметь несколько связанных Issues.

Пока предлагается исследовать модель «родительская conformance Issue на проект
плюс дочерние Issues по измерениям» и отдельно определить, нужен ли общий
Project field для состояния соответствия или достаточно вычисляемого отчета.
Процент нельзя вводить без четких критериев и весов: иначе он создаст ложную
точность. Отдельный эпик для этой модели — [Issue #11](https://github.com/vernikr/mother/issues/11),
а его первые подзадачи — [#12](https://github.com/vernikr/mother/issues/12) и
[#13](https://github.com/vernikr/mother/issues/13).

## 10. Источники и проверка

- Фактическое состояние Project: `gh project view 1 --owner vernikr --format json`.

- Items Project: `gh project item-list 1 --owner vernikr --format json --limit 100`.
- Views и workflows: GraphQL queries к `organization(login: "vernikr")` и
  `projectV2(number: 1)`.
- Issue #1: `gh issue view 1 --repo vernikr/mother --json ...`.
- Предыдущий отчет: [`01-structure-and-files.md`](01-structure-and-files.md).
- Направление владельца:
