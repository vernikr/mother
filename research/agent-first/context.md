# Контекст проекта методологической матрицы

> Статус: исходный бриф, зафиксированный 2026-10-15. Это не утвержденная
> методология и не набор обязательных правил; дальнейшие решения требуют
> согласования с владельцем проекта.

## Зачем существует этот проект

Проект должен постепенно выработать единую методологию ведения всех проектов
владельца: структуру каталогов, набор ключевых файлов и их форматы, правила
ведения документации и состояния, детальную модель корневого `AGENTS.md`,
структуру GitHub Project и регламент ее ведения, dev- и CI/CD-обвязку, а также
связанные с этим практики.

Итоговый артефакт должен быть образцом (матрицей), по которому можно:

- разворачивать новый проект;
- приводить существующий проект к согласованному виду;
- постепенно улучшать проект без требования одномоментного завершения;
- выбирать подходящий вариант в зависимости от типа проекта, а не навязывать
  одну неподвижную структуру всем репозиториям.

## Ориентиры и границы

- За основу берутся современные конвенциональные практики сообщества.
- Практики адаптируются под agent-first разработку и конкретный контекст
  проектов владельца.
- Нельзя считать текущую структуру проектов ограничением: ее изменение не
  имеет для владельца существенной стоимости.
- Для всех проектов планируется использовать GitHub Projects как систему
  управления проектами. Поэтому методология должна заранее определить, какие
  сведения являются источником истины в GitHub Projects, какие живут в
  репозитории, а какие только ссылаются друг на друга.
- Проекты сильно различаются по платформам, языкам, стекам, интерфейсам,
  уровню зрелости и ключевому пользователю (агент или человек).
- Приоритет — не разовая «готовая система», а эволюционное развитие самой
  матрицы и проектов, которые она описывает.
- Матрица должна подстраиваться под собственные принципы: ее структура,
  документация, проверки и история решений должны служить примером описываемой
  методологии.
- Любое существенное изменение самой матрицы должно быть согласовано с
  владельцем проекта.

## Модель работы человека и агентов

Разработка ведется полностью с помощью ИИ-агентов. Владелец проекта:

- не смотрит исходный код;
- не просматривает диффы, коммиты и pull request;
- не проверяет результаты тестов напрямую;
- лишь изредка проверяет верхнеуровневую документацию;
- использует терминал, системные настройки и логи только по конкретной просьбе
  агента;
- может выполнить вручную лучше агента глубокое веб-исследование, поскольку
  располагает большими вычислительными ресурсами для него.

Отсюда следует рабочая гипотеза методологии: репозиторий должен быть понятен,
проверяем и управляем прежде всего агентом, а человеческое управление должно
осуществляться через короткие, надежные и регулярно обновляемые документы,
автоматические проверки, наблюдаемое состояние и явные запросы к владельцу.
Это гипотеза для проверки исследованием, а не окончательное правило.

## Первый исследовательский вопрос

Какова оптимальная, переносимая между платформами, языками, стеками, IDE и
моделями структура каталогов и набор ключевых файлов для долгоживущих проектов,
которые полностью разрабатываются ИИ-агентами, когда человек направляет работу,
но не просматривает код, диффы, коммиты, pull request и тестовые результаты?

Нужно выяснить:

1. к какой конвенции сообщество пришло на 2026-10-15;
2. какие менее распространенные, но полезные практики появились в последнее
   время;
3. какие практики действительно универсальны, а какие зависят от платформы,
   стека, интерфейса или типа пользователя;
4. как оптимизировать их под agent-first контекст владельца;
5. какие элементы следует сделать обязательными, условными или запрещенными;
6. как поддерживать такую структуру эволюционно и без ручного code review.

## Материалы и доступные ориентиры

`projects-overview.md` — инвентарь 37 GitHub-репозиториев владельца, снятый
2026-10-13 и отсортированный по числу коммитов. Его следует использовать как
карту разнообразия и источник кандидатов для стратифицированного изучения, но
не как ограничение будущей методологии.

Для первой волны особенно релевантны проекты с ключевым пользователем Agent:
`research-workspace`, `size-report`, `biblio-mcp`, `browser-agent`,
`browser-agent-mcp`, `gemini-mcp`, `gemini-router`, `freebuff-watchdog`,
`freebuff-bridge`, `yt-transcript-api` и `size-report-sandbox`. Для контроля
полезно сравнивать их с несколькими human-first проектами сходной роли.

## Правила работы с чувствительными данными

Доступ к GitHub при необходимости должен предоставляться через локальное
окружение или штатный credential helper. Токены, пароли, cookie, приватные
payload и иные секреты не сохраняются в этом репозитории, исследовательских
заметках, логах или итоговых отчетах.

## Что еще не решено

Первый исследовательский отчет сохранен в
[`01-structure-and-files.md`](01-structure-and-files.md). Его рабочий вывод:
GitHub Issue должен быть единицей работы, GitHub Projects — операционной
проекцией очереди и состояния, а репозиторий — источником durable knowledge,
планов длинных изменений, решений и проверяемых процедур. `TODO.md` не следует
делать вторым master-backlog; `docs/state.md` нужен как компактный handoff с
указателями и командами повторной проверки, а не как копия Project.

- окончательная таксономия типов проектов и профилей зрелости;
- обязательный минимум файлов для любого проекта;
- граница между корневой документацией, агентскими инструкциями и локальными
  правилами каталогов;
- формат состояния, решений, handoff, журналов и evidence;
- роль GitHub Issues/Projects/Actions и внешних систем, включая границу между
  GitHub Projects и файлами планов/to-do;
- допустимый уровень дублирования: какие поля синхронизируются автоматически,
  какие дублируются только как кэш для агента, а какие не должны дублироваться;
- протокол обновления GitHub Projects агентом и поведение при расхождении
  карточки, issue и документа в репозитории;
- политика изменений самой матрицы и ее автоматической проверки;
- критерии, по которым владелец получает короткий управленческий отчет вместо
  технических деталей.

Эти пункты должны решаться через отдельные исследования и согласованные
решения, а не молча встраиваться в первый черновик.
